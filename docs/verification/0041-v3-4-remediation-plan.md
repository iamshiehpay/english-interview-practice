# Contract 3.4 remediation proposal — approval pending

This is a prospective diagnostic plan, not a change to the 3.3 release result. The frozen 3.3 raw outputs, pre-feedback labels, semantic reviews, thresholds, and `BLOCKED` report remain authoritative for that run. No new model request is authorized by this document.

## Evidence and decision

- The 3.3 offline review passes automatic constraints for 60/60 outputs, stability for 80/80 dimensions, and AI-persona Practice Loops for 5/5. It fails the pre-approved label comparison for 40/60 outputs and independent bilingual semantic review for 1/60. The no-model release check reproduces both failures from `evaluation/results/codex-v3-3-reviewed.json`.
- The 40 failed outputs contain 59 one-level rating misses: relevance 11, support 17, structure 27, English expression 4. Structure is below the approved range in 26/27 misses. An independent audit of all 27 structure reasons found that 13 of the 22 approved-4/model-3 misses withhold level 4 for brevity or insufficient development; nine import missing task content or outcomes into structure. Nineteen of the 27 structure misses oppose unanimous blind-drafter structure labels. These are diagnostic classifications, not ground truth.
- Only 12 of the 40 failed outputs miss structure alone. Even perfect correction of structure on the frozen inputs would raise the output-level pass count from 20/60 to at most 32/60. Relevance, support, English expression, and bilingual parity need independent attention. The 3.2 and 3.3 packets are not controlled before/after samples because their questions and blind labels differ.
- In `embedded-role-fit` repeat 1, the Chinese support reason names reproducible tests while the English reason says only “a concrete way.” The transcript supports the detail, but the bilingual reasons do not express the same detail. Surface bilingual checks cannot establish semantic equivalence; independent review stays required.

## Candidate contract change, before any new output

The exact proposed instruction is generated by `evaluation/v3-4/contract-candidate.js` from the untouched 3.3 contract; it is not wired into production. For a new contract version, retain the current four 1–4 dimensions and all automatic constraints. Add a dimension-isolation check to the feedback instruction: score structure from the transcript's internal organization, even when its content is off topic or incomplete; a brief but clear causal or stepwise progression can earn 4, one claim with a simple reason or two merely related statements earns 3, weak links impeding thought earn 2, and 1 requires no discernible organization. A structure reason must describe an organizational feature, never an omitted task part, example, result, or conclusion. Relevance should name which requested part is or is not answered; support should identify which question-related point the evidence or reasoning actually advances. English expression remains about language only. Before returning JSON, reconcile each level with its own dimension's anchor and rationale, without changing the other dimensions to compensate.

For every English/Traditional-Chinese coaching pair, draft the English assessment first and render only that assessment into Traditional Chinese. Keep each named action, mechanism, limitation, and recommendation at the same specificity in both languages. If either language names a detail absent from its counterpart, revise the pair before returning JSON. Continue to quote the original transcript in the shared quote field only. This is an instruction to the model, not a claim that a deterministic translation checker can prove parity.

Do not change approved label ranges, release thresholds, the old outputs, or the semantic review verdict. Do not add a case-specific rule keyed to the failed 3.3 IDs. A production contract change requires a new version and separate artifacts/checksums so 3.3 remains reproducible.

## Proposed paid/subscription diagnostic stage

**Approval requested for two explicitly capped kinds of new model use:** at most **16 Codex subscription feedback requests** (no analysis calls or automatic retries), and at most **four independent AI reviewer agent invocations** (one invocation each for two pre-output Role-persona drafts, one pre-output approval, and one post-output semantic/label audit; no retry or replacement invocation without renewed approval). Failed or interrupted requests count against their respective caps. The eight new synthetic question/transcript pairs are saved in `evaluation/v3-4/pilot-inputs.json`, two per diagnostic group: brief coherent sequence, off-topic but internally organized answer, missing outcome with ordered checks, and relevance/support/expression plus bilingual-detail stress. The two drafters and approver freeze one- or adjacent-level expectations and evidence for all eight inputs before the candidate receives feedback. Freeze the exact candidate instruction, model configuration, inputs, labels, source hash, and request ledger. Call the candidate feedback method twice per input in an isolated, non-production process, saving every output and failure without rewriting it. This diagnostic stage does not exercise the app UI or server; the later full evaluation must do that. Do not use port 4310 or real practice data.

An independent reviewer then checks all saved bilingual pairs and compares every dimension to the frozen expectations. This pilot is **diagnostic only** and cannot turn the v1.0.0 release gate green. Advance to a separately approved full run only if all 16 outputs satisfy the unchanged automatic constraints, all bilingual pairs pass independent semantic review, at least 12/16 outputs meet every frozen rating range, and no dimension misses in more than four outputs. These are pilot go/no-go criteria, not a substitute or relaxation of the 60-output release gate. If the pilot misses this bar, stop new calls and diagnose; do not adjust labels after seeing outputs.

A later release-capable run would require five live analyses and sixty live feedback results on a new frozen blind packet, with a separately stated request cap that includes retries, then independent semantic and label review. The changed feedback contract also requires deciding whether the five persona loops must be repeated against the new behavior. v1.0.0 may be reported as AI-validated only when its actual versioned offline report passes every existing gate.
