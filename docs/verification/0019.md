# Issue 0019 verification — interpret a natural-language job request

Date: 2026-09-21. Implementation by the main agent. **No independent review yet**
(the reviewer hit an API session limit; see issue 0016's note).

| AC | Evidence |
|---|---|
| A request in Chinese or English yields separate confirmable fields | `POST /api/discovery/interpret` returns a proposal keyed by all seven profile fields; the browser renders only the fields the learner actually stated |
| An unstated field comes back empty, never guessed | Asserted twice: a fully-stated request leaves `exclusions` empty, and a request stating nothing yields every field empty |
| The learner can edit or clear any field before confirming | The proposal fills the existing editable inputs; the browser edits `exclusions` afterwards and saves |
| Nothing is saved until confirmed | The saved profile is compared byte-identical before and after interpreting, at the API and in the browser |
| An invalid provider output is rejected and the profile is unchanged | Seven malformed shapes (wrong type, extra key, missing `salary` key, empty string, over-length list, over-length term, null) each return 502 with the saved profile untouched |
| Searching with the saved profile and no new request still works | Asserted with a stub job source |
| A legacy six-field profile loads with an empty salary | Asserted on write and on read; `validateProfile` requires only the six original fields |
| Cancellable, retryable, idempotent per request identifier | A gated provider proves one call for two identical `X-Request-Id` requests; the operation appears as `interpret` in `/api/operations` |
| The interface states the request text is sent to the model | `#interpret-disclosure` names the configured provider, or says the demonstration service sends nothing outbound |
| Deleting all local data removes the saved profile | Asserted, including the stored proposal |

Automated evidence: `node --test test/search-interpretation.test.js` — 7/7 pass.
`npm test` — 151/151 pass. `npm run test:browser` — PASS, including describing a
job in Chinese, seeing the understood criteria, confirming them, and editing a
field afterwards.

Implementation notes worth flagging:

- The proposal is persisted as `jobSearchProposal`, separate from
  `jobSearchProfile`. It has to be stored for the operations tracker to replay a
  repeated request identifier without calling the provider twice. Storing it does
  **not** make it the learner's criteria: only confirming writes the profile.
- The Job Search Profile gained a seventh field, `salary`. Writes accept the six
  original fields and default `salary` to empty, so profiles written by an earlier
  version still validate.
- The 找職缺 view had no entry in the main navigation and was effectively
  unreachable; it now has one.

Limits and what is **not** verified:

- The demonstration provider's interpreter is a fixed keyword matcher, not a
  model. It proves the confirm-before-search flow and the "never guess" rule, and
  is **no evidence at all** about how well a real model reads a learner's sentence.
  Quality with a configured provider is pending human validation.
- Salary is stored as the learner's own words and is not parsed into a number or
  used for filtering in this issue.
- The curated shortlist, the Fit Breakdown, multi-source search and the
  no-results relaxations are issue 0020 and are not implemented here.
