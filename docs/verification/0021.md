# Issue 0021 verification — listening mode

Date: 2026-09-21. Implementation by the main agent. No independent review yet.

| AC | Evidence |
|---|---|
| Toggle beside the question read-aloud control in all four places | Mounted wherever a question is read aloud: the question screen, a Practice Record, a Follow-up Question and a Short Mock Session question. It is passed the question text and its Chinese meaning; the Illustrative Answer and correction rewrites get no `hideable`, so no toggle appears there |
| Off by default, current behaviour unchanged while off | Browser smoke asserts the toggle exists, is unchecked, and the question is visible |
| Remembered across screens and a page reload | Persisted in `localStorage`; verified in a real browser across a genuine reload (`persistedAcrossReload: true`, `storedValue: "on"`). A module-level listener keeps every mounted control in step within a page |
| Storage refusal still works | Both the read and the write are wrapped in `try/catch`; a browser that refuses storage simply runs with the mode off |
| Pressing play hides the English question and its Chinese meaning | Asserted in the smoke test; hiding happens *before* the request so the learner cannot read ahead while the audio loads |
| A reveal control is visible the whole time and reveals in one click | `顯示題目` is un-hidden with the text and asserted in the smoke test |
| No auto-reveal when the audio ends | The smoke test waits for playback, then waits again and asserts the question is still hidden |
| Another question starts hidden again | Each mount renders fresh with the text visible and hides on its own next play |
| A read-aloud failure reveals the question immediately | Asserted in the smoke test with a stubbed 503, and **observed in a real browser**: the demo tone failed to play and the question was revealed with 「朗讀失敗，已顯示題目，可再試一次。」 |
| No toggle when the provider cannot speak | `mountReadAloud` returns early when `canSpeak` is false, so neither the control nor the toggle is rendered |
| Hidden text is out of the accessibility tree | The `hidden` attribute is used, not a visual-only class. Verified in a real browser: `hidden: true`, `display: none`, `offsetParent: null` |
| Turning the mode off while hidden reveals the text | Asserted in the smoke test |
| No schema, record or HTTP contract change | Presentation only; `npm test` unchanged at 163/163 and no server file was touched |

Automated evidence: `npm test` — **163/163 pass** (unchanged; this issue adds no API
surface). `npm run test:browser` — **PASS**, including the full listening-mode walk.

Real-browser verification: default off, enable, reload, reopen the practice, confirm
the mode persisted, confirm hiding removes the text from the accessibility tree, and
confirm a failure reveals it.

Limits and what is **not** verified:

- **Whether it is actually useful for listening practice is a human judgement**, and
  is pending learner acceptance. Nothing here says the mode teaches anything.
- Audible playback is still unverified in this environment (see
  [the third-round record](./third-round-0014-0020.md)); the failure path was
  exercised precisely because playback failed.
- The preference is per browser and per device, and is lost when site data is
  cleared. That is deliberate: it is a display preference, not practice data, so it
  is not stored in the Practice Record.
- No screen reader was actually run. The evidence is that hidden text is removed
  from the accessibility tree by the `hidden` attribute, not an observation of
  assistive-technology behaviour.
